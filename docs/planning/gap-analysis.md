# Logo Generator 구현 전 갭 분석

작성일: 2026-09-12 · 역할: Metis 읽기 전용 분석 · 소유 범위: 이 문서만

## 결론

**기존 Codex 플러그인에 대화형 스킬 하나를 추가하고, 내장 이미지 도구를 직접 사용하며, 파일 검증·세션 저장만 작은 로컬 도구로 구현하는 구성을 권장합니다.** 웹 앱, MCP 서버, OpenAI API 클라이언트는 현재 요구를 충족하는 데 필요하지 않습니다. 로고 서비스 5곳의 브라우저 조사·스크린샷과 최종 실행 계획은 코디네이터 소유이며, 이 문서는 해당 조사를 수행하거나 완료했다고 주장하지 않습니다.

가장 중요한 선행 결정은 ① 실제 생성 호출 주체, ② 새 대화에서 복구할 상태, ③ 검증 가능한 산출물의 범위입니다. 시안을 설명하거나 프롬프트를 작성한 것만으로 이미지 생성 기능을 구현했다고 판정해서는 안 됩니다.

## 확인한 저장소 상태

- 추적 파일은 `.codex-plugin/plugin.json`, `README.md`, `.gitignore`, `skills/.gitkeep` 네 개입니다. 분석 중 다른 작업자가 만든 `docs/`, `plans/` 디렉터리는 보존했습니다.
- manifest는 `name: logo-generator`, `version: 0.1.0`, `skills: ./skills/`이며 설명과 기본 프롬프트는 개발용 초기 문구입니다. 실행 가능한 스킬, 앱, 서버, 패키지 설정, 테스트, CI는 없습니다.
- 로컬 `plugin-creator/scripts/validate_plugin.py`로 현재 저장소를 검사하여 **Plugin validation passed**를 확인했습니다. 이는 포장 형식의 통과이며 로고 생성 동작의 증거는 아닙니다.
- 환경에는 Python, uv, Node, Bun, Codex CLI가 있습니다. 특정 런타임 버전·패키지 설치 여부·새 대화의 이미지 도구 사용 가능 여부는 이 검사로 보장하지 않습니다.

## 1. 권장 아키텍처와 범위

| 계층 | 책임 | 포함하지 않을 책임 |
| --- | --- | --- |
| `skills/logo-generator/SKILL.md` | 브리프 정리, 필요한 질문, 콘셉트 제안, 실제 내장 이미지 생성·수정, 결과 비교·선택·내보내기 | 도구 호출 흉내, 별도 로그인 UI, 임의 API 전환 |
| `references/` | 이미지 도구 연결 규칙, 브리프·수정·산출물 계약, 선택적으로 읽는 세부 절차 | 다른 개인 설치 경로의 스킬이 반드시 있다고 가정하는 의존성 |
| 작은 로컬 helper | 세션 읽기·저장, 파일 복사·검사, 버전별 산출물 기록 | 셸에서 내부 이미지 도구를 호출할 수 있다고 가장하는 SDK wrapper |
| workspace 세션·출력 디렉터리 | 복구 가능한 브리프, 시안·수정 이력, 실제 이미지 | 설치된 플러그인 캐시를 사용자 데이터 저장소로 사용 |

브리프에는 브랜드명과 로고에 들어갈 정확한 문구, 업종·대상, 분위기, 선호·금지 요소, 활용처를 담습니다. 이미 제공된 정보는 다시 묻지 않고, 결과를 바꿀 중요한 빈칸만 짧게 확인합니다. 사용자가 바로 생성을 요청하고 정보가 충분하면 별도 승인 단계 없이 진행합니다. 콘셉트 수는 요청을 따르며, 여러 시안을 요청한 경우 각 파일과 선택 가능한 식별자를 제공합니다.

공식 문서는 스킬만 담은 플러그인도 지원하고, 스킬을 명시적으로 호출하거나 설명에 따라 자동 선택한다고 설명합니다. 따라서 별도 웹 UI보다 현재 Codex 대화가 자연스러운 사용 표면입니다. [플러그인 구성](https://learn.chatgpt.com/docs/build-plugins), [스킬 호출 및 구성](https://learn.chatgpt.com/docs/build-skills)

## 2. 내장 이미지 도구와 API를 구분하는 계약

- **기본 경로:** 현재 호스트가 제공하는 실제 `image_gen` 도구입니다. 이 분석 세션에서는 `image_gen__imagegen`이 노출되어 있습니다. 내장 경로는 사용자에게 `OPENAI_API_KEY`를 요구하지 않으며, 플러그인 manifest 자체가 이미지 생성 권한을 만들어 주는 것은 아닙니다.
- **API 경로:** 별도 인증·요금·SDK·응답 상태 계약을 갖는 선택 기능입니다. 내장 도구가 없거나 실패해도 사용자의 명시적 API 선택 없이 자동 전환하지 않습니다. API Responses의 `previous_response_id`, `image_generation` tool 설정은 Codex 내장 도구 인자가 아닙니다.
- 현재 세션의 실제 도구 인자는 `prompt`, `referenced_image_paths`, `num_last_images_to_include`입니다. `model`, `size`, `quality`, `background`, `out`, `previous_response_id`를 내장 호출에 추가하지 않습니다. 원하는 결과 특성은 프롬프트에 표현하고 반환 파일에서 확인합니다.
- 저장 위치를 도구 인자로 보장하지 않습니다. 실제 반환된 파일 경로 또는 반환된 이미지 데이터를 근거로 저장하고, 전용 파일 검사를 거쳐 프로젝트 출력에 복사합니다. 생성 전후의 디렉터리에서 단순히 “가장 최근 파일”을 고르면 병렬 작업의 이미지를 잘못 가져올 수 있습니다.
- 도구 미노출, 오류, 파일 미반환은 미완료 상태로 기록합니다. placeholder PNG, 직접 만든 SVG, 문서 속 tool-call 예시를 실제 생성 결과로 제시하지 않습니다.

공식 문서는 내장 생성과 API 사용을 별도 경로로 구분하며, API 다중 턴 편집은 이미지 문맥 또는 응답 ID를 통해 구성합니다. 이것이 내장 도구에 같은 인자가 존재한다는 뜻은 아닙니다. [내장 이미지 생성](https://learn.chatgpt.com/docs/image-generation), [Image API 및 Responses API](https://developers.openai.com/api/docs/guides/image-generation)

**문서 간 차이:** 설치된 imagegen 스킬의 CLI 기본 모델 설명과 현재 API 문서의 모델 구성이 다릅니다. 이번 기능에 API 모델명을 고정하거나 최신 API 기능을 내장 도구의 보장으로 옮기지 마십시오. 실제 실행에는 현재 세션 도구 스키마를 우선하고, API 기능을 별도 도입한다면 그때 공식 문서를 다시 확인합니다.

## 3. 수정·참조 이미지 의미

| 사용자 의도 / 입력 | 실행 및 저장 규칙 |
| --- | --- |
| 새 로고, 이미지 없음 | 새 생성입니다. 두 참조 인자를 모두 생략합니다. |
| 기존 시안에서 색상만 변경 | 해당 시안을 수정 대상으로 고정하고, 나머지 문구·배치·실루엣 등 보존 조건을 프롬프트에 명시합니다. |
| 로컬 파일을 수정 | 아직 보지 않았다면 먼저 `view_image`로 확인한 뒤 현재 도구의 `referenced_image_paths`를 사용합니다. |
| 대상 중 대화 첨부만 있고 로컬 경로가 없음 | 모든 대상을 포함하는 최소 `num_last_images_to_include`를 사용합니다. 현재 상한은 5이며 경로 인자와 동시에 보내지 않습니다. |
| 어느 방식으로도 모든 수정 대상을 포함할 수 없음 | 누락 이미지를 다시 첨부받습니다. 내용만 추정하여 수정했다고 표시하지 않습니다. |
| 이미지가 분위기·스타일 참고용 | 새 생성 의도를 유지하고 입력별 역할을 표시합니다. 스타일 참조를 수정 대상이나 사용자가 선택한 로고로 오인하지 않습니다. |

대화의 “두 번째 것”은 안정적인 시안 ID로 해석하고, 수정본에 `parent_artifact_id`를 남깁니다. 원본을 덮어쓰지 않고 새 버전을 저장합니다. 새 대화에서는 복사해 둔 이미지 파일을 다시 읽으므로 과거 대화 첨부나 임시 참조 인덱스가 계속 유효하다고 가정하지 않습니다.

이 규칙 중 구체적인 인자명·5개 제한은 **현재 세션 도구 계약**의 관측값입니다. 로컬 imagegen 스킬의 일반 설명보다 구체적인 현재 스키마가 우선하며, 이를 모든 Codex 버전에 대한 영구 호환성 주장으로 문서화하면 안 됩니다.

## 4. 세션 지속성

권장 저장 위치는 `<workspace>/.logo-generator/sessions/<session-id>/`이며 최종 전달 파일은 `<workspace>/output/logo-generator/<session-id>/`입니다. 사용자 지정 출력 위치가 있으면 이를 따릅니다. 설치 캐시나 개발자의 절대 홈 경로에 상태를 묶지 않습니다.

최소 상태에는 다음을 포함하는 것이 좋습니다.

- `schema_version`, `session_id`, `revision`, 생성·갱신 시각, 현재 단계.
- 브리프와 사용자 문구 원문, 명시한 가정, 선택한 콘셉트·시안 ID.
- 생성·수정 작업 ID, 사용한 최종 프롬프트, 입력별 역할·파일 경로, 부모 시안 ID, 상태(`pending`, `succeeded`, `failed`).
- 실제 출력의 상대 경로, SHA-256, 감지된 형식·크기, 알파 검사 결과, 시각 검토 여부.
- 실패 이유와 마지막으로 성공한 산출물. 인증 정보나 이미지 전체 base64를 상태 JSON에 중복 저장하지 않습니다.

불변 조건: 파일 저장·검사에 성공하기 전에는 작업을 성공으로 기록하지 않습니다. 파일과 상태 저장을 원자적으로 처리하고, 기존 파일 덮어쓰기 및 동시에 열린 대화의 오래된 revision 갱신을 거부합니다. 상태 파일이 손상됐거나 스키마가 미지원이면 기존 데이터를 보존한 채 설명 가능한 오류를 반환합니다. 모호한 “마지막 세션” 대신 복수 세션 목록·명시적 세션 선택을 제공합니다.

재개 시 선택된 파일의 존재와 해시를 확인하고 누락 파일은 복구를 요청합니다. 실패한 작업을 재개했다고 같은 유료 생성 호출을 자동 반복하거나, 대화 history를 가진 것처럼 행동하지 않습니다. 테스트에는 새 프로세스에서 저장 상태만으로 재개하는 경우를 포함해야 합니다.

## 5. PNG·투명도·벡터에 대한 정직한 산출물

- **PNG:** 확장자만 확인하지 말고 실제 디코더로 파일 형식·크기·내용을 읽습니다. 다른 형식이 반환되면 실제 형식을 알리거나 명시한 변환 과정으로 PNG를 만듭니다. 파일 이름 변경은 변환이 아닙니다.
- **투명 배경:** 프롬프트 요청과 검증 결과를 구분합니다. 알파 채널 존재만으로 충분하지 않으며, 실제 투명 픽셀과 보이는 로고 픽셀이 모두 있어야 합니다. RGBA이지만 alpha가 전부 255인 이미지, RGB 체크무늬 배경, 완전 투명한 빈 이미지는 통과하지 못합니다. 팔레트 PNG의 투명도도 검사 대상으로 삼습니다.
- **시각 확인:** 알파 통계는 필요조건입니다. 밝고 어두운 배경 위의 결과를 직접 확인하여 테두리 잔상·잘림·체크무늬가 픽셀로 남는 문제를 잡습니다. 정확한 문구, 작은 크기에서의 식별성, 수정 중 보존 조건도 확인합니다.
- **벡터:** 내장 이미지 결과는 래스터로 취급합니다. “vector style” 프롬프트는 편집 가능한 SVG/EPS/AI 생성 보장이 아닙니다. 래스터를 `<image>`로 넣은 SVG나 PNG만 넣은 PDF를 벡터라고 안내하지 않습니다. 진짜 벡터가 필요하면 별도 재작성·트레이싱과 검증이 필요하다고 명확히 표시합니다.
- **완료 보고:** 파일 경로, 실제 형식·크기·투명도, 생성 또는 수정 여부, 선택된 버전, 검토 결과를 짧게 제공합니다. 폰트 파일·상표 등록 가능성·독점 권리·인쇄용 CMYK 등의 확인되지 않은 보장을 덧붙이지 않습니다.

공식 API 문서도 출력 형식과 배경 옵션을 구분하고, 문구 정확성·브랜드 일관성에 한계가 있음을 설명합니다. API의 투명 출력 옵션을 내장 도구의 전용 인자처럼 사용할 수는 없습니다. [출력 형식과 한계](https://developers.openai.com/api/docs/guides/image-generation)

## 6. 패키징 제약과 주의점

1. 이미 존재하는 `.codex-plugin/plugin.json`을 유지하며 관련 메타데이터만 갱신합니다. 새 scaffold를 `--force`로 덮어쓰지 않습니다. 디렉터리와 manifest 이름은 `logo-generator`로 일치해야 합니다.
2. `skills/logo-generator/SKILL.md`의 frontmatter에는 유효한 `name`, `description`을 넣고, 지원하는 시작·수정·재개 요청을 정확히 설명합니다. 암묵적 호출은 기본값을 유지합니다. `agents/openai.yaml`을 넣으면 `default_prompt`에 `$logo-generator`를 명시합니다.
3. 내장 이미지 도구를 허구의 MCP 서버로 등록하지 않습니다. `dependencies.tools[].type`은 현재 로컬 규격에서 `mcp`만 지원하므로 내장 도구 의존성은 스킬 본문에서 설명합니다. `.mcp.json`·`.app.json`은 실제 기능이 없으면 추가하지 않습니다.
4. 로컬 plugin-creator 참조의 JSON 예시에는 `hooks`가 있으나 **SKILL.md의 필수 규칙과 실제 validator는 이를 거부합니다.** 이번 manifest에 `hooks`를 넣지 마십시오.
5. 현재 공식 문서는 root `plugin.json`의 portable 형식과 `.codex-plugin/plugin.json` 호환 형식을 구분합니다. 이 저장소는 설치된 creator와 validator에 맞는 후자를 이미 사용하므로, 요청 없는 포맷 전환이나 이중 manifest는 피합니다. [공식 호환 형식 설명](https://learn.chatgpt.com/docs/build-plugins)
6. 참조·스크립트·아이콘 경로는 플러그인 내부에서 해석되어야 합니다. 다른 환경으로 복사하거나 공백이 있는 경로에 설치해도 동작하는지 확인합니다. 개발자 홈의 스킬 경로를 배포 파일에 고정하지 않습니다.
7. 설치가 범위에 포함되면 기존 marketplace 이름·source를 helper로 확인한 뒤 공식 cachebuster·재설치 흐름을 사용합니다. 개인 marketplace 기본 위치는 `~/.agents/plugins/marketplace.json`이며 수동 수정이나 팀 marketplace 생성으로 확장하지 않습니다. 새 대화에서 스킬 발견과 실행을 확인합니다. 설치가 없었다면 View/Share 링크나 설치 완료 문구를 만들지 않습니다.

## 7. 테스트 인프라 권고와 수용 기준

추천 기반은 **uv + Python + Pydantic v2 + Pillow**, 개발 검사는 **pytest + Ruff + basedpyright**입니다. 브리프·상태는 명시적 스키마로 파싱하고, 이미지 디코딩은 검증된 라이브러리에 맡깁니다. PNG 디코더를 새로 구현하거나 단순 텍스트 스킬만을 위해 웹 프레임워크를 도입할 이유는 없습니다. 버전은 구현 때 결정하고 `pyproject.toml`과 lockfile로 고정합니다.

단위·통합 검사는 임시 workspace에서 API 키와 네트워크 없이 반복 가능해야 합니다. CI는 macOS 개발자 홈의 creator 경로에 의존하지 않아야 합니다. 로컬 공식 validator는 작성 검증에 추가 사용하고, 저장소의 패키징·상태·이미지 검증 테스트는 별도로 재현 가능하게 구성합니다.

| 수용 시나리오 | 필요한 관측 증거 |
| --- | --- |
| 브리프부터 첫 생성 | 스킬이 읽히고 실제 내장 이미지 호출 후 열리는 파일이 생성됩니다. 문구·비율·활용 목적을 직접 검토합니다. |
| 여러 시안 중 특정 안 선택 | 각 파일과 ID가 독립적으로 존재하고 선택한 ID가 저장됩니다. 시안 모음 이미지 한 장을 독립 파일 여러 개로 세지 않습니다. |
| 선택한 로고 색상만 수정 | 정확한 부모 파일을 참조한 도구 호출, 수정본, 원본 보존, 문구·실루엣 시각 검토가 확인됩니다. |
| 참조용 이미지와 수정 대상 혼재 | 서로 다른 역할·대상을 정확히 기록하고 현재 도구 인자 규칙을 지킵니다. |
| 새 대화에서 재개 | 상태와 로컬 파일만 다시 읽어 선택 시안·브리프·수정 이력을 복구합니다. |
| 내장 도구 없음·생성 실패 | 성공 산출물이나 API 자동 전환 없이 오류 상태와 기존 작업을 보존합니다. |
| 투명 PNG 검증 | 실제 투명·가시 픽셀이 있는 PNG는 통과하며, opaque RGBA·RGB 체크무늬·완전 투명·손상 PNG는 거부합니다. |
| 형식·경로 공격 및 충돌 | JPEG를 `.png`로 바꾼 파일, 상태 경로 탈출, symlink 탈출, 기존 파일 충돌, 오래된 revision 갱신을 안전하게 처리합니다. |
| 한국어·공백 경로·입력 | 브랜드 문구와 경로를 훼손하지 않으며 셸 명령 문자열에 사용자 입력을 직접 삽입하지 않습니다. |
| 벡터 요청 | 실제 벡터 파일이 없으면 SVG/EPS/AI 제공 완료로 표시하지 않습니다. |
| 설치 및 패키징 | plugin·skill validator 통과, 깨끗한 위치에서 참조·helper 실행, 설치 범위라면 새 대화에서 발견·호출까지 확인합니다. |

권장 fixture는 소형 opaque RGB PNG, opaque RGBA PNG, 부분 투명 RGBA PNG, 팔레트 투명 PNG, 완전 투명 PNG, PNG로 위장한 JPEG, 절단 PNG, 정상·손상·미지원 버전 상태 JSON입니다. 테스트가 만든 이미지라는 출처를 표시하고 실제 생성 증거와 분리합니다. 손상 파일·중간 실패·덮어쓰기·재개·충돌 같은 사용자 데이터 불변 조건을 검증하며 문서 문구나 제목 존재만 검사하는 테스트로 대체하지 않습니다.

**자동 테스트의 통과만으로 내장 이미지 생성 통합을 증명할 수 없습니다.** 최종 QA에는 실제 생성 1회와 그 결과를 입력으로 한 실제 수정 1회 이상, 결과 파일·프롬프트·참조 관계·시각 검토 증거가 필요합니다. 당시 도구가 없으면 mock 테스트 결과와 실행 미검증 상태를 분명히 구분해야 합니다. 새 대화 재개는 별도 실제 스킬 사용 시나리오로 확인합니다.

## 코디네이터가 최종 계획에 확정할 사항

- 위 최소 아키텍처와 세션·출력 경로를 채택할지 결정해 구현 소유 범위를 분리합니다.
- 5개 사이트 각각의 실제 방문 URL, 관찰 일시, 스크린샷 파일, 관측한 입력→시안→수정→내보내기 흐름을 조사 문서와 연결합니다. 로그인 뒤 기능·유료 출력은 관찰 여부를 표시합니다.
- 조사 결과에서 실제 제품 결정으로 이어진 근거를 기록합니다. 예: 이름·업종 입력, 시안 비교, 색상 수정, 명확한 다운로드 형식 안내를 Codex 대화로 옮기는 이유입니다.
- “코드 구현”, “내장 도구로 생성·수정”, “설치 후 새 대화 사용”의 완료 기준을 각각 정합니다. 설치 범위는 원 사용자 요청과 기존 승인에 따라 판단하며 이 분석이 별도 승인을 요구하지는 않습니다.
